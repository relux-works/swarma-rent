# Учётные записи на хостинге кода

Каждый запрос на слияние открывает чья-то учётная запись, даже когда работу сделал агент. Чья это запись, решает три вещи сразу: какой секрет существует и где он лежит, кто может отобрать доступ без согласия другой стороны и чьё имя пострадает, если агент поведёт себя плохо. Глава сравнивает четыре модели учётной записи и говорит, какую когда выбирать.

Жёсткой зависимости от одного хостинга у сервиса нет. Каждый сервис описан своим адаптером, и хостинг кода любого вида служит для службы действий одним адаптером из многих (книга Swarma, глава "Учётные данные и логины", раздел "Шлюз учётных данных и адаптеры сервисов"). Глава пользуется GitHub и GitLab как двумя примерами. Свойства этих сервисов приведены по их открытой документации на ноябрь 2026 года; адаптер каждого сервиса проходит квалификацию на точной версии API, и каждое свойство подтверждает эта квалификация.

## Четыре модели

**Приглашённая учётная запись арендодателя.** Арендодатель держит на хостинге учётную запись агента. Арендатор приглашает её в свою организацию или в отдельные репозитории и даёт ей роль. Агент действует под именем арендодателя, а право ему дал арендатор приглашением.

**Публичная работа под учётной записью арендодателя.** Агент открывает задачи и запросы на слияние в публичных репозиториях, где у арендатора нет никаких прав. Доступа никто не выдаёт: его даёт сама публичность репозитория. Агент действует под именем арендодателя, и отвечает за это имя арендодатель.

**Приложение или токен арендатора.** Арендатор создаёт в своей системе собственную машинную личность и ограничивает её названными репозиториями. В GitHub это собственное приложение арендатора (GitHub App), установленное на выбранные репозитории. В GitLab это токен доступа проекта или группы: GitLab сам создаёт для него служебного пользователя с ролью. Секрет этой личности арендатор заводит у брокера своего хоста. Агент действует под именем, которое принадлежит арендатору.

**Общее приложение арендодателя.** Арендодатель держит одно приложение на хостинге, и каждый арендатор устанавливает его на свои репозитории. Секрет один, и он у арендодателя: ключом приложения можно получить доступ к репозиториям любого арендатора, который его установил.

## Сравнение

| Свойство | Приглашённая запись арендодателя | Публичная работа | Приложение или токен арендатора | Общее приложение арендодателя |
| ----- | ------ | ------ | ------ | ------ |
| Чья личность | Арендодателя | Арендодателя | Арендатора | Арендодателя |
| Какой секрет существует | Токен учётной записи арендодателя | Токен учётной записи арендодателя | Ключ приложения или токен проекта арендатора | Ключ приложения арендодателя |
| Где лежит секрет | У брокера хоста арендатора, если запись своя на каждого арендатора | У общей службы публичных действий | У брокера хоста арендатора | У общей службы арендодателя |
| Область | Роль в организации или репозитории; область токена задаёт арендодатель | Всё публичное | Названные репозитории и названные права | Репозитории каждой установки |
| Кто отбирает доступ | Арендатор исключает запись; арендодатель отзывает токен | Владельцы чужих репозиториев блокируют запись | Арендатор удаляет приложение или отзывает токен | Арендатор удаляет установку |
| Что отдаёт утечка секрета | Все репозитории, куда запись приглашена | Право писать от имени арендодателя | Репозитории одного арендатора в пределах прав | Репозитории всех арендаторов |
| Связь между арендаторами | Есть, если запись общая | Общая репутация записи | Нет | Общий секрет |
| Что делает арендатор в конце | Исключает запись из организации | Ничего | Удаляет приложение или отзывает токен | Удаляет установку |

Строка "связь между арендаторами" решает больше остальных. Правило одного арендатора говорит о хостах; учётная запись на хостинге кода может нарушить его в обход, если один секрет открывает данные двух арендаторов. Общее приложение арендодателя нарушает его прямо: ключ приложения это секрет, общий для всех арендаторов, и он не может лежать на хосте одного из них. Приглашённая запись нарушает его, когда одна запись служит нескольким арендаторам: её токен на хосте первого арендатора открывает репозитории второго.

## Приложение или токен арендатора

Эту модель книга рекомендует как основную.

В GitHub арендатор создаёт приложение в своей организации, выбирает права, например запись содержимого и запись запросов на слияние, и устанавливает приложение только на нужные репозитории. Право приложения покрывает репозиторий целиком; писать только в названные ветки агента заставляет служба действий по полям доверенности. Ключ приложения он заводит у брокера. Половина адаптера, которая работает у брокера, получает по ключу короткоживущий токен установки и обновляет его; по документации GitHub такой токен действует один час и может быть дополнительно сужен до части репозиториев и прав. Шлюз учётных данных и служба действий получают служебную аренду токена установки, а ключ приложения брокер не выдаёт никому.

В GitLab арендатор создаёт токен доступа проекта или группы с ролью и сроком. Действия агента видны под именем служебного пользователя, который принадлежит проекту арендатора. На собственной установке GitLab модель работает на любом тарифе; на общем сервисе GitLab токены проекта и группы зависят от тарифа, и это арендатор проверяет у себя.

Свойства модели таковы. Область задаёт арендатор средствами своей системы, и сервис аренды не может её расширить. Отобрать доступ арендатор может в любой момент без арендодателя: удалить приложение или отозвать токен. Действия агента в журнале аудита системы арендатора записаны под личностью, которой управляет арендатор. Секрет существует только у брокера одного хоста и в системе арендатора. Двух арендаторов модель не связывает ничем.

Цена модели это работа арендатора: создать приложение или токен и завести секрет. Интерфейс заведения ведёт его по шагам и показывает точный набор прав, который требует адаптер.

## Приглашённая учётная запись арендодателя

Модель годится там, где у хостинга нет ни приложений, ни токенов проекта, или где арендатор не хочет заводить никаких секретов.

Условие, без которого модель недопустима: своя учётная запись на каждого арендатора. Арендодатель держит пул учётных записей; бронь берёт запись из пула, арендатор приглашает именно её, а токен этой записи лежит только у брокера хоста этого арендатора. Токен принадлежит арендодателю, поэтому заводит его служба размещения при подготовке хоста: запросом, который зашифрован на ключ приёма брокера и подписан ключом поставщика; блокировку аккаунта для такого токена снимает арендодатель. После аренды арендодатель отзывает токен и возвращает запись в пул только после того, как арендатор её исключил. Одна запись на всех арендаторов запрещена по причине из раздела "Сравнение". Там, где условия хостинга не дают одной организации держать несколько машинных учётных записей, модель не предлагается.

У модели три слабости. Область токена учётной записи обычно шире, чем нужно: роль в организации даёт запись больше, чем права приложения. Действия агента записаны под личностью арендодателя, и арендатор видит в своём журнале чужое имя. Учётная запись в организации арендатора может занимать оплачиваемое место, а условия хостинга ограничивают машинные учётные записи; оба обстоятельства арендодатель проверяет до того, как предлагает модель.

## Публичная работа под учётной записью арендодателя

Агент, который чинит ошибку в чужом открытом проекте, действует в системе, где ни у арендатора, ни у арендодателя нет прав. Доступ здесь ограничить нечем, и доверенность ограничивает поведение: что агент публикует, куда и как часто. Нарушение бьёт по имени арендодателя и по остальным арендаторам, которые пользуются той же записью. Токен этой записи общий для арендаторов, поэтому на хосте арендатора его нет: публикует общая служба публичных действий, которая работает под собственным пользователем ОС на машине без агентов. Служба действий хоста передаёт ей запрос агента вместе с доверенностью; исполнителем в доверенности на публичные записи назван ключ общей службы, и она проверяет доверенность на своей ноде. У публичной работы пять обязательных ограничений.

Первое: список целей. Манифест называет публичные репозитории поимённо. Разрешения "любой публичный репозиторий" в сервисе нет.

Второе: запись идёт через ответвление. Служба публичных действий отправляет ветку в ответвление репозитория, которое принадлежит учётной записи арендодателя, и открывает запрос на слияние из него. Права записи в чужой репозиторий агенту не нужны и не выдаются.

Третье: проверка содержания до публикации. Каждый текст, который выйдет под именем арендодателя, проходит модератора публичных текстов, ключ которого назван в договоре отдельно от ключа модератора сообщений: заголовок и описание запроса на слияние, текст задачи, комментарий. Модератор применяет правила публичной работы из договора: без секретов и чужих данных, без рекламы, с соблюдением правил вклада целевого проекта, с явным указанием, что автор агент. Запрет модератора останавливает одно действие; агент получает отказ с названным правилом. Арендодатель ведёт список проектов, которые не принимают вклад от агентов, и служба публичных действий отказывает по этому списку раньше модератора.

Четвёртое: пределы частоты. Доверенность на записи несёт число записей за период для каждого репозитория; этот вид предела владелец решил добавить 14 ноября 2026 года (глава "Доверенности и деньги"). Сверху действует потолок оператора на учётную запись в целом, общий для всех арендаторов: он защищает запись от блокировки хостингом за слишком частые действия.

Пятое: приёмка у хозяев. Запрос на слияние принимают или отклоняют сопровождающие целевого проекта. Жалоба сопровождающих идёт модератору арендодателя и разбирается как нарушение правил договора.

Одно ограничение остаётся неснятым: репутация записи общая. Блокировка записи хостингом остановит публичную работу всех арендаторов сразу. Арендатор, который сам сопровождает открытый проект, избегает этого моделью "приложение или токен арендатора": для собственного публичного репозитория она работает так же, как для закрытого.

## Общее приложение арендодателя

Модель удобна: арендатор нажимает "установить", ничего не создаёт и не заводит. Книга её не рекомендует, и причина одна. Ключ общего приложения открывает репозитории каждого арендатора, который его установил. Его нельзя положить на хост арендатора, не нарушив правила одного арендатора, поэтому он должен лежать у общей службы, а общие службы по правилу главы "Стороны и службы" секретов арендатора не держат. Утечка этого ключа касается всех арендаторов сразу.

Если владелец сервиса всё же выберет эту модель ради удобства, ей нужна отдельная служба выдачи токенов установки под собственным пользователем ОС на машине без агентов, с тем же уровнем защиты, что у подписанта. Она выдаёт хосту арендатора только токен установки этого арендатора и никогда ключ. Решение записано в главе "Чего не хватает" как вопрос владельцу.

## Личность в коммитах

Учётная запись хостинга и автор коммита это разные личности. Автора коммита задаёт запись системы в манифесте: имя и адрес, под которыми агент записывает коммиты. Мы предлагаем, чтобы коммиты агента подписывал ключ подписи git, созданный на хосте арендатора и не покидающий его. Держит его ключник хоста: слот просит подпись коммита так же, как подпись запроса, и самого ключа не получает. Связь этого ключа с именем арендодателя даёт заявление о ключе; спецификация предлагает для него вид `git-signing-ssh` (LIP-0015, раздел 6). Заявление связывает ключ с именем и полномочий не даёт: подписанный коммит доказывает, что его создала станция этого арендодателя, а право принять коммит остаётся у сопровождающих репозитория.

## Что выбрать

| Случай | Модель | Почему |
| ------ | ------ | --------- |
| Компания с организацией на GitHub | Собственное приложение на выбранные репозитории | Узкая область, короткие токены, отбор доступа без арендодателя |
| Команда на GitLab, общем или собственном | Токен проекта или группы | То же; личность создаёт сам GitLab |
| Один разработчик с личным репозиторием | Токен с областью в один репозиторий или собственное приложение | Самый короткий путь без общей записи |
| Хостинг без приложений и токенов проекта | Приглашённая запись арендодателя, своя на арендатора | Иного способа нет |
| Вклад в чужой открытый проект | Публичная работа под записью арендодателя с пятью ограничениями | У арендатора там нет прав |
| Собственный открытый проект арендатора | Приложение или токен арендатора | Нет общей репутации с другими арендаторами |

Модель записана в манифесте для каждой системы и входит в договор хэшем манифеста. Сменить её в середине срока значит подписать новый договор.

Собственная установка хостинга в закрытой сети арендатора добавляет один вопрос: как хост арендатора её достигает. У хоста свой исходящий адрес, и арендатор открывает доступ этому адресу на своём сетевом экране. Туннель в сеть арендатора сервис не строит: он расширил бы то, что видит хост, далеко за пределы названных репозиториев.
